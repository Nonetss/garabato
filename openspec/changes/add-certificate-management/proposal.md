## Why

The product is a platform to sign PDFs with Spanish digital certificates, in the spirit of AutoFirma but on the web. Every later step (signing, signature history, validation, companies managing their clients' certificates) needs users to keep their certificates in the platform first, so certificate management is the first slice. A standalone proof of concept already confirmed that Bun can open real-world PKCS#12 files (OpenSSL 3, legacy 3DES/RC2 exports, RSA and EC keys) and read the holder's identity, so the risk left is how the platform guards the key material, not whether the stack can handle it.

## What Changes

- Signed-in users can import one or more personal certificates by uploading a `.p12`/`.pfx` file with its password. The server opens it, rejects wrong passwords, files without exactly one private key matching a certificate, already expired certificates and duplicates of a certificate the user already holds.
- On import the platform reads and stores the certificate's public metadata: holder name, given name and surname, NIF/NIE (from the subject `serialNumber`), issuer, serial number, SHA-256 fingerprint, key algorithm and validity period. The user gives each certificate an alias, which they can rename later.
- The PKCS#12 file is stored encrypted at rest with envelope encryption: a random data key per certificate, wrapped by a server master key taken from a new required environment variable. The ciphertext is bound to its row so blobs cannot be swapped between certificates.
- By default the password is never stored: it will be asked on every signature. The user can opt in to **remembering the password** for a certificate (at import or later), which stores it encrypted the same way, and can forget it at any time. Turning it on requires typing the password again, which is verified against the file.
- Users list their certificates with a validity status (valid, expiring within 30 days, expired) and can delete one. Deleting destroys the encrypted file and the remembered password (crypto-shredding) but keeps the metadata row, so future signature history can still name the certificate that was used.
- The API never returns the PKCS#12 file, the private key or the password, and none of them is ever logged.
- A new `/certificates` page in the frontend, registered in the application-surface registry and navbar, with the import dialog, the list, rename, remember/forget password and delete.
- Out of scope, planned as later changes: signing PDFs and object storage for documents, signature history, signature validation, organization-owned certificates for companies and gestorías, expiry notifications and master-key rotation tooling.

## Capabilities

### New Capabilities
- `certificate-management`: importing PKCS#12 certificates per user, reading their metadata, encrypted storage of the file and the optional remembered password, listing with validity status, renaming, remembering/forgetting the password and deleting with crypto-shredding.

### Modified Capabilities
- `environment-configuration`: the server environment gains a required `CERTIFICATE_ENCRYPTION_KEY` (the master key that wraps the per-certificate data keys); it is validated by `@nonete/env/server`, documented in `.env.example` and generated by `scripts/setup-dev.sh` and `scripts/bootstrap.sh`.

## Impact

- **Database** (`packages/db`): a new `certificates` schema module. The agent proposes the schema; the user generates and applies the migration.
- **API** (`packages/api`): a new `certificate` feature under `src/v1/certificate/` wired into the v1 router, with PKCS#12 parsing and encryption modules beside its handler. First procedure in the repo that receives a file upload (multipart through oRPC), well under the existing 1 MiB body limit.
- **Dependencies** (`packages/api`): `node-forge` (PKCS#12 decryption, including legacy formats) and its types. Certificate parsing and the key/certificate match use Bun's built-in `node:crypto` (`X509Certificate`), so no other library is needed.
- **Env and scripts**: `packages/env/src/server.ts`, `.env.example`, `scripts/setup-dev.sh`, `scripts/bootstrap.sh`, `packages/api/tests/setup.ts`, and `compose.prod.yml` if it lists variables explicitly.
- **Frontend** (`apps/frontend`): a new `features/certificates` domain, a `/certificates` route and its entry in `lib/app-surfaces.ts`.
- **Tests**: handler tests for every procedure, unit tests for the PKCS#12 reader (with generated test fixtures, no real certificates) and for the encryption round-trip and tamper detection.
- **Security**: the master key becomes a critical secret. Losing it makes every stored certificate unrecoverable; leaking it together with a database dump exposes the certificates of users who chose to remember their password.
