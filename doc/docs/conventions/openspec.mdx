Cada capacidad del sistema tiene una spec en `openspec/specs/<capability>/spec.md` con requisitos (`SHALL`) y escenarios (`WHEN` / `THEN`). Es la descripción de referencia de cómo debe comportarse. Para verlas:

```bash
openspec list --specs
```

## El ciclo de un cambio

1. **Proponer:** `openspec new change <nombre>` crea la carpeta del cambio en `openspec/changes/<nombre>/`.
2. **Escribir los artefactos:** `proposal.md` (por qué y qué cambia), los deltas de specs en `specs/` (requisitos añadidos, modificados o eliminados), `design.md` (cómo, con decisiones y riesgos) y `tasks.md` (la lista de tareas).
3. **Implementar** las tareas, marcándolas como hechas.
4. **Sincronizar** los deltas con las specs principales.
5. **Archivar** el cambio en `openspec/changes/archive/<fecha>-<nombre>/`.

`openspec status --change <nombre> --json` dice en qué artefacto está un cambio, y `openspec instructions <artefacto> --change <nombre> --json` da las instrucciones para escribirlo. `openspec/config.yaml` fija el esquema `spec-driven` y el contexto del proyecto que se usa al generar los artefactos.

## Con Claude Code

| Comando | Qué hace |
| --- | --- |
| `/opsx:explore` | Pensar un cambio antes de proponerlo |
| `/opsx:propose` | Crear el cambio con todos sus artefactos |
| `/opsx:apply` | Implementar sus tareas |
| `/opsx:sync` | Pasar los deltas a las specs principales sin archivar |
| `/opsx:archive` | Archivar el cambio terminado |

## Comprobar las specs

```bash
openspec validate --specs --strict
```

Comprueba que cada spec está bien formada, en modo estricto. Con `--all` valida también los cambios abiertos.
