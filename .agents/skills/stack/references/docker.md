# Docker and CI

Four compose files, one per way of running the stack: three at the root (dev, production-like, registry) and `apps/gateway/compose.yml`. The root ones run the three app images (frontend, backend, gateway) plus stock `postgres:17`, and `compose.yml`/`compose.prod.yml` add `grafana/loki`.

## `compose.dev.yml` (hot-reloading dev stack)

Project `better-dev`, started by `bun run dev` (`up --build --watch`), removed by `bun run dev:down`. Runs frontend (`astro dev`, `:4321`) and backend (`bun --hot`, `:3000`) from `apps/*/Dockerfile.dev`, `gateway` from its production Dockerfile with `localhost` upstreams and HTTP on `:8080` (as `apps/gateway/compose.yml`), and `db`. **The apps behave exactly like native dev**: frontend, backend and gateway use `network_mode: host`, the apps read the root `.env` with no `environment` overrides and listen on the same `localhost` ports, so the database URL and peer URLs are whatever native dev uses. Host networking needs Linux (or Docker Desktop with host networking enabled).

- `db` (`postgres:17`, container `better-dev-db`, user/password `postgres`, database `better`, volume `db_data`) is on the default network and publishes `${POSTGRES_PORT:-5432}:5432`. The backend waits for its healthcheck. `bun run db:start` starts only this service for native dev (`bun run dev:local`), so both modes share one database.
- No bind mounts: `develop.watch` `sync`s app source (`apps/<app>/src`, the frontend's `public/`) and the `packages/*/src` each service imports (frontend: `api`, `auth`, `env`, `logger`; backend: `api`, `auth`, `cron`, `db`, `env`, `logger`), `sync+restart`s `apps/frontend/astro.config.mjs` and the gateway's Caddyfile, and `rebuild`s on `bun.lock`, the root `package.json` and the app's own `package.json`. **A new TS package or source folder a service imports needs its own `sync` entry.**

## `compose.yml` (production-like, builds from source)

Project `better`, started by `bun run docker:up` (`up -d --build`); `docker:build`, `docker:down`, `docker:logs` are the other root scripts. The app is on `http://localhost:${FRONTEND_PORT:-4444}`.

| Service | Ports | Notes |
|---|---|---|
| `frontend` | `expose` 4321 | Astro SSR only, reached through the gateway. Waits for a healthy backend. Healthcheck `bun -e fetch('http://localhost:4321/login')`. |
| `backend` | `expose` 3000 | Waits for a healthy `db`. Healthcheck `bun -e fetch('http://localhost:3000/')`. |
| `gateway` | `${FRONTEND_PORT:-4444}` → 80 | Caddy (`apps/gateway/`): `/rpc/*`, `/api/*`, `/scalar*`, `/openapi.json` → backend, the rest → frontend. Waits for a healthy frontend. Healthcheck `wget http://localhost/health`. |
| `db` | none | `postgres:17`, password `${POSTGRES_PASSWORD:-postgres}`, database `better`, volume `db_data`. |
| `loki` | `expose` 3100 | Optional log sink (`grafana/loki:3.7.7`, 720 h retention, volume `loki_data`); nothing waits for it. |

Every app reads the root `.env` (`required: false`); container addresses are overridden in `environment` (`references/env.md`).

## `compose.prod.yml` (registry images)

Prebuilt images `ghcr.io/nonetss/stack-{frontend,backend,gateway}:main`, the same five services on a `better` bridge network, all reading one `.env` generated by `scripts/bootstrap.sh` in the deployment directory (`env_file: .env`, required). **Only `gateway` declares `ports`** (`${FRONTEND_PORT:-4444}:80`); every other service uses `expose` or nothing. Keep it that way: a new public route goes in the gateway's site, never as a `ports` entry on another service. The backend migrates the database and seeds the admin on startup, so a deployment needs no manual database step.

## `apps/gateway/compose.yml`

Runs only the gateway on the host network for native dev (`bun run gateway`): HTTP on `:8080`, upstreams `localhost:3000` and `localhost:4321`.

## Dockerfiles

- `apps/backend/Dockerfile`, `apps/frontend/Dockerfile` — build and run on `oven/bun:${BUN_VERSION}-slim` (no Node; `BUN_VERSION` is an `ARG` kept in sync with the root `packageManager`; compose healthchecks use `bun -e`). Copy every workspace manifest first, `bun install --frozen-lockfile` (cache mount `/root/.bun/install/cache`), then `COPY . .` + build with `SKIP_ENV_VALIDATION=1` — dependency changes are the only thing that busts the install layer. Runtime images ship no `node_modules`: the backend copies `dist` plus `packages/db/src/migrations` (resolved as `../../packages/db/src/migrations` from `WORKDIR apps/backend`); the frontend copies `dist` and runs `dist/server/entry.mjs` on `HOST=0.0.0.0`, `PORT=4321`.
  - **When adding a Bun workspace, add its `package.json` COPY line to both.**
- `apps/gateway/Dockerfile` — `caddy:2-alpine` plus the Caddyfile; no build step. The frontend image has no proxy of its own.
- `apps/{backend,frontend}/Dockerfile.dev` — dev images for `compose.dev.yml`: same dependency layer as prod, `CMD` is the app's dev server (`bun run --hot src/index.ts`, `bun run dev --port 4321`). Production Dockerfiles and CI never use them. **When adding a Bun workspace, add its `package.json` COPY line to both `Dockerfile.dev`s too.**
- `.dockerignore` keeps `node_modules`, build outputs, Dockerfiles, `compose.yml` and every `.env*` (except `.env.example`) out of the build context.

## CI

`.github/workflows/docker-build.yml` — on pushes to `main`, detects which images changed (backend: `apps/backend/`, `packages/`, root manifests; frontend: `apps/frontend/`, `packages/`, root manifests; gateway: `apps/gateway/`; the workflow itself and `.dockerignore` rebuild all) and builds and pushes those of the three (`…-backend`, `…-frontend`, `…-gateway`) to `ghcr.io/<owner>/<repo>-<app>` on GitHub-hosted `ubuntu-26.04` runners (login with the workflow's `GITHUB_TOKEN`, `packages: write`; no secret to configure) with a registry layer cache. Tags: `latest`, branch name, `<branch>-<sha8>`. It runs no lint, type-check or test step.
